# 苍穹外卖（sky-take-out）性能测试方案

## 1. 文档目的与范围

### 1.1 目的

针对苍穹外卖微服务系统（Spring Boot 3.5.0 + Spring Cloud 2025.0.0 + Spring Cloud Alibaba 2025.0.0.0）开展系统性性能测试，达到以下目的：

1. 验证系统在目标容量下各核心接口的吞吐量、响应时间、错误率是否满足业务要求。
2. 定位性能瓶颈（网关、服务、数据库、Redis、Seata、RocketMQ 等），为扩容、索引、连接池、缓存策略调优提供依据。
3. 验证 Sentinel 两层限流（Gateway 100 QPS、订单核心写接口 5 QPS、AI 接口 5 QPS）和熔断降级规则是否按预期生效。
4. 验证订单链路中 Seata 分布式事务、RocketMQ 异步消息、WebSocket 推送在高并发下是否出现数据不一致、消息积压或连接泄漏。
5. 验证长时间运行下的稳定性（GC、内存、连接池、线程池、消息积压）。

### 1.2 测试范围

**纳入范围**

- 客户端 → `sky-gateway` → 业务微服务的全链路 HTTP 接口性能。
- 微服务间 OpenFeign 调用链路：`order-service ↔ user/cart/menu-service`、`cart-service ↔ menu-service`、`agent-service ↔ menu/cart/order-service`。
- 中间件：Nacos、MySQL（5 个业务库）、Redis、Sentinel、Seata、RocketMQ。
- 关键业务链路：浏览菜单、购物车、地址簿、提交订单、支付、订单状态流转、报表导出、AI 点餐助手、订单通知与 WebSocket 推送。
- 单接口基准测试、混合业务容量测试、稳定性/疲劳测试、尖峰冲击测试、限流熔断专项测试。

**不纳入范围**

- 前端页面/小程序渲染性能（本次仅测 API）。
- 阿里云 OSS 真实上传性能（默认使用本地/Mock 对象存储，不测公网 OSS）。
- 微信支付真实通道（项目当前为模拟支付实现）。
- K8s 多副本弹性扩缩容测试（项目尚未完成 K8s 编排；若环境具备可追加双副本扩展测试）。

### 2.2 关键性能设计（来自代码与 Nacos 配置）

| 层 | 机制 | 对性能测试的影响 |
|---|---|---|
| 网关 | 全局 JWT 校验 + 注入 `X-User-Id`/`X-User-Role` | 所有受保护接口均增加 JWT 解析开销；压测必须携带有效 Token |
| 网关 Sentinel | 全局 100 QPS | 超过 100 QPS 返回 HTTP 429 + `Result{code:0}`，属于**预期行为** |
| order-service Sentinel | `submitOrder`/`payOrder`/`userCancelOrder`/`confirmOrder`/`rejectOrder`/`adminCancelOrder`/`completeOrder` 各 5 QPS | 写接口压测超过 5 QPS 会返回 `Result{code:0,msg:"请求过于频繁…"}` |
| agent-service Sentinel | `agentChat`/`agentChatStream` 各 5 QPS | AI 接口成本高，限流为预期保护 |
| 熔断 | RT>300ms 或异常比例>50%，窗口 10s，minRequestAmount=5 | 若被测接口真实 RT 超过 300ms，可能触发熔断，需区分"性能差"与"熔断保护" |
| Seata AT | `OrderTransactionService.submitOrderInTransaction()`/`paymentInTransaction()` 使用 `@GlobalTransactional` | order/cart 两个参与库写 `undo_log`，需关注锁冲突和日志表增长 |
| RocketMQ | 订单状态变化异步发送 `order-notification`；admin-service 双消费者组 | 下单/支付/取消等接口主链路不受 MQ 阻塞，但需监控消息积压和消费者写入 |
| Redis | `dish_{categoryId}` 缓存、`setmealCache::categoryId`、`agent:chat:memory:{userId}` | 首次访问冷缓存会回源 MySQL；压力应区分冷/热缓存 |
| 支付 | 测试环境为模拟支付，不调用微信支付 API | 支付接口性能只代表当前模拟实现 |

## 3. 性能测试目标与验收指标

> 本项目未在需求中给出明确 SLO。以下为**建议首轮验收基线**，正式执行前需与产品/研发确认真实业务容量目标；如已有 SLO，以 SLO 为准。

### 3.1 通用指标

| 指标 | 建议通过标准 |
|---|---:|
| 业务请求错误率 | 正常容量场景 < 0.1%；限流熔断场景允许预期 `code=0`/429 |
| 中间件可用性 | 测试期间 Nacos/MySQL/Redis/Seata/RocketMQ 无宕机、无数据损坏 |
| 资源水位 | 稳态 CPU < 70%，内存无持续增长，磁盘无写满 |
| 日志 | 无 OOM、死锁风暴、连接池耗尽、持续 `Connection timeout` |

### 3.2 分场景指标（首轮建议值）

| 场景 | 目标吞吐 | 平均 RT | P95 | P99 | 错误率 |
|---|---:|---:|---:|---:|---:|
| C 端菜单浏览（热缓存） | 网关总 80 QPS | < 150ms | < 300ms | < 500ms | < 0.1% |
| C 端购物车读/写 | 50 QPS | < 300ms | < 500ms | < 800ms | < 0.1% |
| C 端地址簿 | 50 QPS | < 200ms | < 400ms | < 600ms | < 0.1% |
| 提交订单（Baidu Mock） | 5 QPS（Sentinel 阈值） | < 1000ms | < 1500ms | < 2000ms | 0（业务态） |
| 订单支付（模拟支付） | 5 QPS | < 500ms | < 800ms | < 1200ms | 0 |
| 管理端查询（分页/详情/统计） | 20 QPS | < 500ms | < 800ms | < 1200ms | < 0.1% |
| 管理端报表 | 2 QPS | < 2000ms | < 3000ms | < 5000ms | < 0.1% |
| Excel 导出 | 0.2 QPS | < 10s | < 15s | < 20s | < 1% |
| AI 同步对话 | 5 QPS（Sentinel 阈值） | — | < 15s | < 20s | < 1%（不含业务降级） |
| AI SSE 流式 | 5 QPS（Sentinel 阈值） | 首字 < 5s，完整 < 30s | — | — | < 1% |
| 混合业务峰值 | 建议 100 QPS（网关限流边界内） | 综合 < 500ms | 综合 < 1000ms | — | < 0.1% |
| 稳定性 8 小时 | 峰值 60%~70% | 与容量场景一致 | 无明显劣化 | — | < 0.1% |

## 4. 测试环境设计

### 4.1 推荐环境拓扑

```text
┌──────────────────────┐        ┌────────────────────────────────────────────┐
│ 压测机（独立）          │        │ 被测环境（Docker Compose 部署）               │
│ - JMeter 控制机/从机   │ HTTP  │ - sky-gateway :8081                       │
│ - 数据工厂脚本          ├──────►│ - 6 个业务服务 + 中间件容器                  │
│ - 监控采集脚本          │        │ - MySQL 建议独立部署/独立数据盘              │
└──────────────────────┘        └────────────────────────────────────────────┘
```

### 4.2 建议资源

| 角色 | 建议配置 | 说明 |
|---|---|---|
| 压测机 | 8C16G × 1~3 台 | JMeter 分布式；压测机与 SUT 网络同网段，RTT < 1ms |
| 应用/中间件宿主机 | 16C32G，SSD | 单机 Docker 部署仅用于中小容量；正式容量建议应用与中间件分离 |
| MySQL | 独立 8C16G SSD | 当前 Compose 用宿主机 MySQL（`host.docker.internal`），压测重点是 DB |
| JVM | 每服务 `-Xms512m -Xmx1g`（订单/网关建议 1.5g） | 当前 Dockerfile 未显式设置堆大小，需通过 `JAVA_OPTS` 固化 |
| 网络 | 千兆以上，避免限速 | 避免 VPN、Wi-Fi 环境 |

### 4.3 环境准入

1. 使用与待测版本一致的镜像/构建产物，记录 Git commit 与镜像 tag。
2. `docker compose ps` 全部 healthy；`/actuator/health` 均 UP。
3. Nacos 已导入 `nacos_config_example/` 下 YAML 与 Sentinel JSON 规则，并确认 Data ID 正确。
4. **特别核查**：Gateway 全局限流采用“API 分组 + 流控规则”两段配置：
   - `sky-gateway-api-group.json`：将 `/admin/**`、`/user/**`、`/notify/**` 归入 `sky-gateway-all`；
   - `sky-gateway-flow-rules.json`：对 `sky-gateway-all` 按 `resourceMode=1` 限制 100 QPS。
   两个 Data ID 都必须已导入 Nacos，并确认 Gateway 数据源拉取成功，否则无法验证“网关总计 100 QPS”。
5. 确认 Sentinel Dashboard 显示 Gateway 流控规则、order 7 个写接口流控/熔断规则、agent 2 条流控规则已加载。
6. 日志级别调为 `INFO/WARN`：当前多个服务 `application.yml` 将 `com.sky.mapper` 设为 `debug`，压测前必须关闭 SQL 调试日志，否则日志 IO 会严重污染结果。
7. MySQL 开启 slow query log（建议 `long_query_time=0.5`）与 `performance_schema`。
8. 外部依赖 Mock 就绪（见 4.4）。

### 4.4 外部依赖处理

| 外部依赖 | 代码位置 | 压测策略 |
|---|---|---|
| 百度地图 Geocoding / 路线规划 | `OrderServiceImpl.checkOutOfRange()`，每次下单 3 次 HTTPS 调用，且 GET 未设置超时 | 强烈建议压测环境使用 **Mock**：通过测试配置项或测试分支替换为本地桩，返回固定坐标与 800m 距离；否则百度 API 配额/延迟将主导下单接口结果 |
| 微信 code2session | `UserServiceImpl.wxLogin()` | 压测不调用 `/user/user/login` 真实登录，改用测试脚本直接生成合法 JWT（见 5.2） |
| 微信支付 | `OrderServiceImpl.payment()` | 当前已是模拟实现，无需处理 |
| 阿里云 OSS | `CommonController.upload` | 除非专项测试上传，否则不纳入混合场景 |
| LLM（OpenAI 兼容接口） | `sky-agent-service` | 压测使用本地 **Mock LLM Server**，模拟 1~3s 延迟、返回菜品推荐文本，并按需返回 tool_call；仅做一次低并发真实模型冒烟测试以验证配置 |

### 5.2 Token 与参数化

- 管理端 Token：通过 `POST /admin/employee/login`（`admin/123456`，MD5 已内置）在 JMeter `setUp Thread Group` 登录一次，提取 `data.token` 作为 JMeter 属性。
- 用户端 Token：不调微信接口。测试脚本用 `jjwt` 按项目算法离线批量生成：
  - 算法：HMAC-SHA256，密钥为 `SHA-256("itbast")` 的 32 字节。
  - Claim：`userId=<压测用户ID>`；过期时间 2 小时。
  - 生成 50,000~100,000 个 Token 到 CSV，供不同线程绑定不同用户，避免共享热点。
- 参数化 CSV：`userId, token, addressBookId, cartDishId, cartSetmealId, orderId, orderNumber`。
- 订单号：提交订单后从响应 `data.orderNumber` 提取，供支付、详情、取消脚本使用；每个用户一次只保留一个可支付订单。
- 关键查询参数：
  - 菜品列表：`GET /user/dish/list?categoryId=11`
  - 套餐列表：`GET /user/setmeal/list?categoryId=13`
  - 订单分页：`GET /user/order/historyOrders?page=1&pageSize=10`
  - 管理端订单：`GET /admin/order/conditionSearch?page=1&pageSize=20&status=&beginTime=…&endTime=…`

### 5.3 缓存预热

压测前统一预热：
- `dish_{categoryId}`：对 100 个分类逐一请求一次。
- `setmealCache::categoryId`：同上。
- JVM JIT 与连接池预热：先用 20% 目标负载跑 10 分钟，不计入结果。

### 5.4 数据恢复

每个场景结束后或每轮测试前，执行标准化重置：

1. 清空并重灌 `sky_order_db`、`sky_cart_db`、`order_notification`。
2. 清理 Redis 新增 key（`dish_*`、`setmealCache::*`、`agent:chat:memory:*`）或整体 flush 后重新预热。
3. 检查并清空 RocketMQ 积压消息、Seata `global_table/branch_table/lock_table`。
4. 记录 `AUTO_INCREMENT` 和表空间大小，供前后对比。

### 6.6 SC-05 C 端订单生命周期

**脚本 A：下单 → 支付**（每个用户必须预先有非空购物车和有效地址）

1. `POST /user/order/submit`
   ```json
   {
     "addressBookId": ${addressBookId},
     "amount": 88.00,
     "deliveryStatus": 1,
     "estimatedDeliveryTime": "2026-08-25 18:00:00",
     "packAmount": 2,
     "payMethod": 1,
     "remark": "",
     "tablewareNumber": 1,
     "tablewareStatus": 1
   }
   ```
2. 提取 `data.orderNumber`。
3. `PUT /user/order/payment`，请求 `{"orderNumber":"${orderNumber}","payMethod":1}`。

**脚本 B：查询与取消**
- `GET /user/order/historyOrders?page=1&pageSize=10`
- `GET /user/order/orderDetail/{id}`
- `PUT /user/order/cancel/{id}`（仅待接单及以前状态）
- `POST /user/order/repetition/{id}`（再来一单）
- `GET /user/order/reminder/{id}`（派送中订单催单，触发 MQ）

**负载**：提交/支付各 5 QPS 以内；查询 20 QPS；取消 5 QPS。
**前提**：Baidu Mock 已启用；Seata Server 正常；RocketMQ 正常。
**观察点**：
- 下单写事务由 `OrderTransactionService.submitOrderInTransaction()` 承担：orders 插入、order_detail 批量插入、Feign 清空 cart；地址读取、地图校验、购物车读取、MQ 发送均在全局事务外。
- 高并发下 Seata 全局锁冲突、`undo_log` 增长、订单金额/购物车状态是否一致。
- `order_detail` 无 `order_id` 索引；`orders` 无 `(user_id,status,order_time)` 复合索引，大数据量时重点关注。

### 6.10 SC-09 AI 点餐助手

请求：`POST /user/agent/chat` 与 `POST /user/agent/chat/stream`，body：
```json

```

- 普通文本回复（1~3s 可配延迟）；
- tool_call 返回（触发 getShopStatus/getDishes/addToCart 等）；
- 可注入失败/超时。

**执行**：
1. 5 QPS 阈值内，同步/流式分别压测 20 分钟。
2. 多轮记忆场景：同一 userId 连续 5 轮对话，验证 Redis 读写与滑动窗口 20 条。
3. 工具调用场景：请求触发 1~3 次工具调用，记录 Feign 到 menu/cart 的放大比。
4. 超过 5 QPS 的限流验证（见 SC-10）。

**指标补充**：同步接口端到端 RT（受 Mock LLM 延迟影响）；SSE 首包时间、完整响应时间、连接数；Redis `agent:chat:memory:*` 数量与内存。

### 6.11 SC-10 Sentinel 限流与熔断专项

| 用例 | 方法 | 预期结果 |
|---|---|---|
| 网关全局限流 | 混合读接口总 120~150 QPS 持续 5 min | 超 100 QPS 部分返回 HTTP 429，body `{"code":0,"msg":"系统繁忙，请稍后再试"}`；业务服务不被打垮 |
| order 写接口限流 | `submitOrder` 以 10 QPS 压测 | 超 5 QPS 返回 HTTP 200 + `{"code":0,"msg":"请求过于频繁，请稍后再试"}`；数据库订单数 ≈ 5 QPS×时长 |
| AI 接口限流 | `agentChat` 以 10 QPS 压测 | 超 5 QPS 返回 `{"code":0,"msg":"当前咨询人数较多…"}` |
| 慢调用熔断 | Mock LLM 延迟 > 300ms，持续满足 `minRequestAmount=5` | 触发 degrade 后返回 `当前服务不可用…`，恢复后自动关闭 |
| 异常比例熔断 | 对带 Sentinel 资源接口注入 50% 异常 | 同上，验证窗口 10s |
| 规则持久化 | 重启 Dashboard，Nacos JSON 规则不丢失 | 规则仍生效 |

**注意**：实测过程中正常容量场景若 P95 普遍 > 300ms，可能触发熔断；应把“性能不达标”和“熔断保护生效”分开记录。

### 6.12 SC-11 混合业务峰值场景

建议业务比例（可按实际埋点调整）：

| 业务组 | 占比 | 主要接口 |
|---|---:|---|
| C 端浏览菜单 | 45% | category/dish/setmeal list |
| C 端购物车 | 20% | cart list/add/sub |
| C 端地址/订单查询 | 15% | address list、historyOrders、orderDetail |
| 管理端查询 | 10% | order conditionSearch、employee/dish page |
| 订单写 | 5% | submit/payment/cancel（保持 ≤5 QPS） |
| 报表 | 3% | workspace、report |
| AI | 2% | agent chat/stream（≤5 QPS） |

执行：总 50 QPS → 80 QPS → 100 QPS 阶梯，每阶 30 分钟；观察全链路资源与错误率。

### 6.13 SC-12 稳定性/疲劳测试

- 使用 SC-11 的 60~70 QPS 混合脚本连续运行 8 小时。
- 每 30 分钟记录一轮：RT 分位数、错误率、JVM heap/GC、线程数、Druid 活跃连接、MySQL 连接与慢查询、Redis 内存、RocketMQ 消费位点与积压。
- 通过标准：结束与开始相比 P95 劣化 < 20%，内存无持续上涨，MQ 积压趋于 0，无连接泄漏。

### 6.14 SC-13 尖峰冲击与恢复

- 在 50 QPS 稳态基础上，5 分钟内将混合流量提升至 200 QPS（预期网关限流），随后恢复 50 QPS。
- 记录：冲击期 429/错误率、各服务 CPU/线程/连接池峰值；恢复后 10 分钟内 RT 是否回到基线；是否出现雪崩。

### 6.15 SC-14 MQ 与 WebSocket 专项

- 消息吞吐：以 5 QPS 提交订单 + 支付/取消/完成组合，使生产速率最大化，观察 Broker TPS。
- 消费积压：运行 30 分钟，检查 `order-notification` 各 Tag 的生产/消费差值、RocketMQ Dashboard 消费进度。
- 幂等性：对同一 `msg_id` 重复投递，验证 `order_notification` 唯一索引去重。
- WebSocket：建立 200/500/1000 个 WS 连接，触发订单状态变更，统计推送时延与到达率；关注 `WebSocketServer` session 集合是否无上限、广播是否阻塞。
- 消费者异常：模拟 admin-service 短暂重启，验证集群消费重平衡、广播消费不丢/不重复。

### 6.16 SC-15 Seata 并发一致性专项

**前置检查**：一笔正常下单在 `seata.branch_table` 中应出现 **2 个分支**（order-service `sky_order_db` + cart-service `sky_cart_db`）；只有 1 个分支说明 cart-service 未正确接入。

- 使用 `test.seata.fault-point=after-cart-clean` 做回滚验证：订单/明细回滚，购物车恢复下单前快照。
- 同一用户并发提交同一购物车（例如 2 线程同时 `submitOrder`），验证：是否产生重复订单/购物车清空竞态。
- 高并发下支付同一订单，验证状态流转只成功一次、两个库的 `undo_log` 均正常清理。
- 若环境允许，可注入 Seata TC 短暂不可用，验证文档所述“降级为本地事务”的行为与数据一致性。
- 统计 `global_table/branch_table/lock_table` 行数变化与锁等待。

### 7.1 脚本规范

1. 每个场景独立 `.jmx`，使用变量化 Host、Token、并发数、持续时间。
2. HTTP 请求开启 `KeepAlive`，连接超时 5s，响应超时 30s（AI/导出单独调大）。
3. 响应断言：统一校验 HTTP 200 与 `code` 字段；限流场景按预期断言 `code=0` 或 429。
4. 关闭 JMeter 端“保存响应数据”等影响施压机性能的选项。
5. 每个场景运行前先 1 并发冒烟 2 分钟，确认参数、Token、断言无误。

## 9. 测试实施流程

### 9.1 阶段

```text
环境准备与准入检查
      ↓
数据准备与预热
      ↓
单接口基准（SC-01）

      ↓

      ↓

```

### 9.2 每轮测试步骤

1. 检查环境健康与数据量。
2. 预热 10 分钟（20% 目标负载）。
3. 从低到高梯度加压，每梯度 10~30 分钟。
4. 同步采集监控，记录异常事件。
5. 场景结束恢复数据，清理 Redis/MQ/Seata 残留。
6. 对比指标，若未达标进入分析。

### 9.3 缺陷等级

| 等级 | 定义 | 处理 |
|---|---|---|
| P0 | 服务崩溃/OOM、数据错乱或丢失、死锁、消息丢失、安全漏洞 | 立即停止相关压测，修复后回归 |
| P1 | 核心接口不达 SLO、严重内存/连接泄漏、MQ 持续积压 | 必须修复或给出明确扩容方案 |
| P2 | 非核心接口超时、轻微资源增长、缺索引导致的慢查询 | 排期优化 |
| P3 | 日志噪音、体验级问题 | 可接受，记录 |

## 10. 风险与已知性能隐患（来自代码审查）

| # | 风险点 | 位置/原因 | 压测应对/建议 |

| 1 | 下单接口依赖百度地图 3 次外部 HTTP，且 GET 未设置超时 | `OrderServiceImpl.checkOutOfRange()`、`HttpClientUtil.doGet()` | 压测必须 Mock；生产建议将 URL/超时可配置、考虑地图服务降级 |

| 8 | 网关 JWT 过滤器 `log.info` 打印每个请求身份 | `JwtAuthGlobalFilter` | 建议压测时改为 WARN，减少日志热点 |

## 12. 准出标准

全部满足以下条件，判定性能测试通过：

1. 第 3 章验收指标全部达标，或未达标项已有明确根因、优化方案及业务方认可的替代指标。
2. 无 P0/P1 未关闭缺陷；P2/P3 有排期或豁免说明。
3. Sentinel 限流与熔断专项全部符合预期。
4. 8 小时稳定性测试无资源泄漏、数据一致性符合预期。
5. 订单链路在 Mock 外部依赖下，业务成功率与一致性满足要求。
6. 完成性能测试报告评审并归档。
