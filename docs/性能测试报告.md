## 2. 测试过程中发现的缺陷

### 🔴 DEF-01（P0·环境·已修复）Nacos 缺失 agent 服务 docker 配置

- **现象**：`sky-agent-service` 容器崩溃循环，日志报 `OpenAI API key must be set`。
- **根因**：Nacos 中只有 `sky-agent-service-dev.yaml`，缺失 `-docker.yaml`；容器以 `docker` profile 启动拉不到 `spring.ai.openai.*`。
- **处置**：按模板 `nacos-config-sky-agent-service-docker.yaml` 通过 OpenAPI 补齐（持久化于 MySQL `nacos_config` 库，Docker Desktop 重启后依然有效）。

### 🔴 DEF-02（P0·数据库污染·已修复）购物车表隐藏 `SLEEP(15)` 触发器

- **现象**：提交订单接口**每次固定耗时 ~30 秒**（并发=1 也是如此）；并发 ≥2 时升级为 InnoDB 锁等待超时 → Feign 读超时 → Seata 全局回滚（`Lock wait timeout exceeded` / `TimeoutRollbacking`）。
- **排查路径**（供复盘）：百度地图 Mock 排除 → Nacos 旧实例排除 → MySQL 行锁等待排除（innodb_trx 为空）→ Seata Java 重试排除（Thread.sleep 不进 general_log）→ connector-j/Druid/应用 jar 静态扫描排除 → **TCP 中转抓包证明客户端只发了 DELETE 且 30 秒线上零字节** → general_log 的 `DO SLEEP(15)×2` 系 mysqld 侧生成 → 定位到表对象：
  ```sql
  -- sky_cart_db, 创建于 2026-08-25 23:50:05（人为添加痕迹明显）
  TRIGGER trg_seata_pause_cart_delete
  BEFORE DELETE ON shopping_cart FOR EACH ROW DO SLEEP(15)
  ```
- **机理**：BEFORE ROW 触发器逐行执行；clean 删 2 行 = 2×15s = 30s。事务持锁时长被放大 100 倍以上，直接引发并发雪崩——这是"性能测试暴露功能级缺陷"的典型案例。
- **处置**：`DROP TRIGGER`；复测下单全周期 RT 从 **~30,000ms 降至 p50=209ms / max=236ms**。
- **⚠️ 遗留动作**：建议审计其余 `sky_*` 库的全部 TRIGGERS/EVENTS/ROUTINES（当前 sky 库已确认为 0 触发器）。

### 🟡 DEF-03（P1·应用设计）shopping_cart 缺 `user_id` 索引（方案风险 #3 应验）

- **现象**（触发器存在期间的记录）：并发 clean（`DELETE WHERE user_id=?` 全表扫描）与并发 INSERT 互相阻塞，20~30s 后抛 `Lock wait timeout exceeded`，进而 Feign 30s 超时、Seata `TimeoutRollbacking`、下单失败。
- **分析**：RR 隔离级别下无索引 DELETE 加 next-key 锁于全表行+间隙，任何并发写都会串行化。触发器移除后本轮未再复现失败，但该结构性隐患随数据量增长必然恶化。
- **建议**：`ALTER TABLE shopping_cart ADD INDEX idx_user_id (user_id);`（同批评估 `orders(user_id,status,order_time)`、`order_detail(order_id)`，见方案风险 #2/#3）。

### 🟡 DEF-04（P2·外部依赖）AI 接口真实 LLM 后端延迟不可控

- 12 QPS 冲击验证中，放行的请求大量超时（60s 内 37 例失败，成功仅 5 例，单次端到端 7.5~15s+）。方案风险 #10 应验。
- **建议**：容量/稳定性轮次必须使用本地 Mock LLM Server（方案 §6.10），真实模型仅冒烟。


### 🔴 DEF-05（P0·并发正确性·已修复）同一购物车并发提交生成重复订单

- **发现场景**：SC-15 同一用户 2 线程 barrier 同时提交同一购物车。
- **现象**：两个请求均返回 `code=1`，生成 2 笔订单且 `number` 相同，购物车只清空一次。
- **修复**：`OrderServiceImpl` 增加按 `userId` 的 JVM 级提交串行化；回归后 1 笔成功、1 笔返回「购物车数据为空」，无重复订单。
- **遗留**：当前为单实例锁，多实例部署需 Redis 分布式锁/数据库幂等约束。

### 🔴 DEF-06（P0·并发正确性·已修复）同一订单并发支付重复成功并重复发 MQ

- **发现场景**：SC-15 同一待支付订单 2 线程 barrier 同时调用 payment。
- **现象**：两个请求均返回成功，`order_notification` 产生 2 条 type=1 支付成功通知。
- **修复**：`OrderMapper.updatePayStatusIfPending` 增加 `WHERE status=1 AND pay_status=0` 条件更新，`OrderTransactionService.paymentInTransaction` 校验受影响行数；回归后仅 1 次成功、另 1 次返回「订单状态错误」，MQ 仅 1 条。
- 详细结果见 `docs/性能测试报告-SC13-15.md` §3.3/§3.4。

### ℹ️ 测试工具侧修正（非产品缺陷）

- Token CSV 默认 CRLF 导致 `\r` 混入 Header 被 Netty 拒绝（400）；支付脚本误取 `number` 字段（实为 `orderNumber`）。均已修复。

## 5. 瓶颈分析与优化建议（优先级排序）

1. **【已完成】清除 `trg_seata_pause_cart_delete` 触发器** —— 收益：下单 RT -99.3%。
2. **【P1】`shopping_cart` 增加 `user_id` 索引**，同批补齐 `order_detail.order_id`、`orders(user_id,status,order_time)`（大数据量前必须完成）。
3. **【P2】报表 N+1 / conditionSearch 逐单查明细**（方案风险 #4/#5）：数据量增长后将成管理端瓶颈，建议批量 IN 查询或冗余汇总表。
4. **【P2】`HttpClientUtil.doGet` 无超时 + 地图强依赖**：保留 `sky.baidu.mock` 开关用于压测；生产侧增加可配置超时与降级策略。
5. **【P2】AI 场景引入 Mock LLM** 再做容量与稳定性轮次。
6. 【P3】Gateway `forwardWithUserContext` 每请求 INFO 日志（方案风险 #8），压测下未见明显影响，建议降为 DEBUG。
