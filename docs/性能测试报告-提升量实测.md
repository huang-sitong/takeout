# 性能优化提升量实测报告（JDK21 + 虚拟线程 + 多实例）

> 执行日期：2026-08-27 ｜ 环境：WSL2 + Docker，宿主机 16 核，全栈 11 容器（7 服务 + 4 副本）同机
> 被测端点：`/user/category/list?type=1`（menu 高频读接口）
> 版本：main 分支，全栈已切换 **JDK 21 + 虚拟线程**（`spring.threads.virtual.enabled=true`）

## 1. 测试目的

在完成以下优化后，量化真实的吞吐提升量：
- ① Tomcat 线程池调大（400）——已推广到全部服务
- ② 路径变量 → 精确路径（消除全量 handler mapping 遍历）
- ③ JDK21 + 虚拟线程（官方基准 +50%）
- ④ 多实例水平扩展（menu 2 副本）

## 2. 测试过程中的两个关键前置发现

### 2.1 网关 Sentinel 规则把吞吐锁死在 100 QPS（掩盖一切优化）
- 现状：`sky-gateway-flow-rules.json` 配置 `count: 100`（QPS，拒绝模式），覆盖 `/admin/**`、`/user/**`、`/notify/**` 全部流量。
- 实测：并发压测时网关返回大量 **HTTP 429**，实际成功吞吐被钳制在 ~100 QPS。
- **影响**：在未调高该规则前，任何经网关的压测都测不到真实提升量。
- **处置（本次）**：临时将 `count` 调至 10000 测真实容量，测完已还原为 100。

### 2.2 单进程 Python 压测客户端本身是瓶颈
- `sat_test.py`（asyncio）在 `/actuator/health` 上仅能打 ~240-290 QPS；
- `load.py`（开环定速）高 QPS 目标下超时、上限 ~440 QPS；
- `sat_thread.py`（requests 多线程）波动极大（80 并发 242↔578）。
- **处置（本次）**：改用**多进程闭环压测器**（每进程独立 asyncio 事件循环，绕过 GIL），health 可达 ~670+ QPS，直连 menu 可达 ~1950 QPS，突破了客户端瓶颈。

> 上述两个发现说明：**此前通过网关、用单进程客户端测得的"瓶颈/提升量"结论需要重新审视。**

## 3. 测试方法

| 项 | 说明 |
|---|---|
| 施压工具 | 多进程闭环饱和压测（每进程独立 asyncio，8 进程 × 每进程 C/8 并发） |
| 压测时长 | 每档 20s |
| 被测路径 | `GET /user/category/list?type=1` |
| 对比基线 | `docs/性能瓶颈突破方案.md` 中的历史实测（JDK17 + 400 线程，sat_thread） |
| 网关限流 | 测试期间临时调至 10000，结束后还原 100 |

## 4. 实测结果

### 4.1 单实例 menu 服务：JDK21 + 虚拟线程 vs 历史基线（直连 :8084）

| 并发 | 历史基线 (JDK17,400线程) | 现在 (JDK21+VT) | **提升** |
|:---:|:---:|:---:|:---:|
| 40 | 803 QPS | **1321 QPS** | **+65%** |
| 80 | 677 QPS | **1949 QPS** | **+188%（≈2.9x）** |
| 200 | — | 1471 QPS | — |
| 400 | — | 1295 QPS | — |

- 全程 **0 错误**（HTTP 200 / code=1）。
- 80 并发下 RT：p50=32ms / p95=92ms / p99=148ms。

> 注：历史基线用较弱的 `sat_thread` 客户端测得，提升量部分含客户端因素；但同一端点、同一并发下从 677→1949，服务端能力的提升是显著的。

### 4.2 经网关：多实例 vs 单实例（限流已放开）

| 并发 | 1 个 menu 实例 | 2 个 menu 实例 |
|:---:|:---:|:---:|
| 80 | **1615 QPS** | 1440 QPS |
| 200 | **1139 QPS** | 1057 QPS |
| 400 | **965 QPS** | 922 QPS |

**结论**：加第 2 个 menu 副本**没有提升**网关吞吐（1 实例甚至略高）。瓶颈已从 menu 服务**转移到单实例网关**。

### 4.3 资源占用（200 并发，~1140 QPS 时）

| 容器 | CPU | 内存 |
|------|-----|------|
| sky-gateway | ~170-184%（≈1.7 核 / 16 核） | ~731 MB |
| sky-menu-service | ~150-173%（≈1.6 核 / 16 核） | ~641 MB |

- 网关与 menu 均**未 CPU 饱和**，说明还有余量，当前限制更可能在 Netty 事件循环 / 网关配置 / 客户端侧。

## 5. 结论

| 项 | 结论 |
|----|------|
| 单实例服务端能力 | ✅ **显著提升**（+65% ~ +188%） |
| 网关 Sentinel 100 QPS 规则 | 🔴 **当前最大瓶颈**，必须先调高/细化，否则一切优化被吞掉 |
| 多实例水平扩展 | ⚠️ 被单实例网关挡住，加 menu 副本无效 |
| 下一瓶颈 | **单实例网关**（建议扩网关实例 / 调 Netty 参数后复测） |

## 6. 建议的下一步

1. **调高/细化网关 Sentinel 规则**：将全局 100 QPS 改为按接口、按需配置（或提高总量），释放优化收益。
2. **扩容网关**：当前仅 1 个网关实例，扩容后多实例水平扩展才能体现真实收益。
3. **用标准压测工具复测**：`wrk`/`hey`（需 sudo 安装）做最终验收，规避 Python 客户端上限。
4. **恢复/确认生产配置**：`sky.baidu.mock` 生产必须为 `false`；Sentinel 规则按生产容量重新评估。
