## 1. SC-13 尖峰冲击与恢复

### 1.1 执行配置

| 阶段 | 负载 | 时长 |
|---|---:|---:|
| 基线 | menu_flow 35 QPS + cart_mix 15 QPS（合计 50 QPS） | 120s |
| 尖峰 | menu_flow 140 QPS + cart_mix 40 QPS + address 20 QPS（合计 200 QPS） | 300s |
| 恢复 | menu_flow 35 QPS + cart_mix 15 QPS（合计 50 QPS） | 600s |

### 1.2 实测结果

| 阶段 | 发送 | 成功 | 限流 | 错误率 | 成功 RPS | 菜单 P50/P95 | 购物车 P50/P95 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 基线 | 6,000 | 6,000 | 0 | 0% | 50.0 | 5.9ms / 9.0ms | 9.6ms / 23.7ms |
| 尖峰 | 60,000 | 29,923 | 30,077 | 0%（业务） | **99.7** | 3.4ms / 6.0ms | 5.1ms / 15.9ms |
| 恢复 | 30,000 | 30,000 | 0 | 0% | 50.0 | 4.6ms / 5.8ms | 9.5ms / 17.0ms |

**关键判定**：

1. 冲击期总请求 200 QPS，Gateway 100 QPS 全局限流精确生效：通过 99.7 QPS，限流 30,077 / 60,000 = 50.1%，限流响应为预期 429/`code=0`。
2. 冲击期所有容器健康，业务错误 0，未出现雪崩。
3. 恢复期 10 分钟内 0 错误、0 限流；菜单 P95 从基线 9.0ms 恢复至 5.8ms，购物车 P95 从 23.7ms 恢复至 17.0ms，均优于基线。
4. 资源水位：冲击期容器 CPU 合计峰值 318.8%（单容器最高 gateway 161.5%）；恢复期 CPU 合计峰值降至 61.5%，内存平稳，无连接池耗尽。
5. 原始监控：`results/sc13_monitor.csv`（基线+尖峰）、`results/sc13_recovery_monitor.csv`（恢复期）。

## 2. SC-14 MQ 与 WebSocket 专项

### 2.1 消息吞吐与消费对账

- 压测脚本：`sc14_order_flow.py`，**4 QPS × 360s，共启动 1,440 轮**。
- 每轮动作：加购 → submit（type=3）→ payment（type=1）→ 按比例 user-cancel（type=4）或 admin confirm→delivery→reminder（type=2）→complete（type=5）。
- 选择 4 QPS 是为了在 `submitOrder`/`payOrder` Sentinel 阈值（5 QPS）以下持续稳定生产消息，避免限流干扰 MQ 对账。

| 指标 | 数值 |
|---|---:|
| 提交成功 / 支付成功 | 1,439 / 1,438（各 1 次限流，0 业务失败） |
| 用户取消 / 催单 / 完成 | 333 / 527 / 527 |
| 全周期 RT | p50=123.4ms，p95=150.8ms，max=728.8ms |
| 期望 MQ 消息 | **4,264 条** |
| `order_notification` 实际增量 | **4,264 条** |
| 按 type 对账 | type1=1,438，type2=527，type3=1,439，type4=333，type5=527，**全部精确匹配** |
| `msg_id` 去重后增量 | 4,264（无重复） |
| RocketMQ 消费 Diff | **0**（`mqadmin consumerProgress`） |
| Seata/undo_log 残留 | global/branch/lock 与两库 undo_log 增量均为 0 |

### 2.2 消费者故障/重平衡

- 生产压测运行至 90s 时 `docker stop sky-admin-service`，持续 60s 后重新启动。
- 重启后集群消费者自动重平衡并追平积压；最终通知表增量与生产者动作数**完全一致**，未出现消息丢失或重复。
- 消费进度：`results/sc14_consumer_progress.txt`（Diff Total=0，Inflight Total=0）。

### 2.3 幂等性

- `order_notification.msg_id` 存在唯一索引 `uk_msg_id`。
- 取一条已存在通知，使用相同 `msg_id` 再次插入，返回 `IntegrityError 1062 Duplicate entry ... for key 'order_notification.uk_msg_id'`，表行数与 distinct msg_id 均不变。
- 结论：同 `msg_id` 重复投递会被数据库唯一索引拒绝，消费者侧幂等有效。

### 2.4 WebSocket 规模与推送时延

每个规模建立连接后触发一笔 submit + payment（每客户端应收到 type=3/type=1 两条消息）：

| WS 连接数 | 建立成功率 | 建连耗时 | 消息到达率 | type3 时延 p50/p95 | type1 时延 p50/p95 | 广播扇出 |
|---:|---:|---:|---:|---:|---:|---:|
| 200 | 100%（200/200） | 0.21s | 100%（400/400） | 124ms / 131ms | 11ms / 16ms | 17ms |
| 500 | 100%（500/500） | 0.47s | 100%（1000/1000） | 100ms / 106ms | 12ms / 20ms | 30ms |
| 1000 | 100%（1000/1000） | 0.96s | 100%（2000/2000） | 126ms / 146ms | 22ms / 38ms | 48ms |

- 时延口径：HTTP 动作返回 → WS 客户端收到对应 JSON 消息。
- 1,000 连接下广播扇出仍在 50ms 以内，`WebSocketServer` 使用 `ConcurrentHashMap` + 同步遍历，未见阻塞雪崩或连接错误。
- 原始数据：`results/sc14_ws_200.json`、`sc14_ws_500.json`、`sc14_ws_1000.json`。

## 3. SC-15 Seata 并发一致性专项

### 3.1 两分支前置检查

- 通过外部 MySQL 会话对目标用户购物车加 `FOR UPDATE` 行锁，使 `cleanCart` 阻塞在全局事务内；期间轮询 `seata.branch_table`。
- 同一个 `xid` 观测到 **2 个 AT 分支**：
  - `resource_id = jdbc:mysql://host.docker.internal:3306/sky_order_db`
  - `resource_id = jdbc:mysql://host.docker.internal:3306/sky_cart_db`
- 结论：cart-service 已作为 Seata RM 正常注册分支，前置检查通过。
- 原始数据：`results/sc15_branch_check_clean.json`。

### 3.2 故障注入回滚验证

- `TEST_SEATA_FAULT_POINT=after-cart-clean` 启动 `sky-order-service`。
- 清空购物车后加入 1 菜 + 1 套餐，记录快照，触发下单。

| 检查项 | 结果 |
|---|---|
| 下单响应 | HTTP 500（注入异常，符合预期） |
| 订单增量 | 0 ✅ |
| 订单明细增量 | 0 ✅ |
| 购物车恢复 | 与下单前快照逐行一致（含原 ID） ✅ |
| `sky_order_db.undo_log` / `sky_cart_db.undo_log` | 0 残留 ✅ |
| `seata.branch_table` / `lock_table` | 0 残留 ✅ |

- 原始数据：`results/sc15_fault_injection_postfix.txt`（修复并发缺陷后的复测）。
- 验证完成后 order-service 已恢复为 `TEST_SEATA_FAULT_POINT=none`。

### 3.3 同一购物车并发提交

**修复前（DEF-05）**：两个并发提交均返回成功，生成 2 笔订单且订单号相同，购物车被清空——存在重复订单风险。

**修复后回归**：

| 并发请求 | 响应 | 结果 |
|---|---|---|
| 请求 1 | `code=1`，订单 id=1548 | ✅ 唯一成功 |
| 请求 2 | `code=0`，「购物车数据为空，不能下单」 | ✅ 业务拒绝 |
| 该用户新增订单 | 1 笔 | ✅ 无重复订单 |

- 修复方案：`OrderServiceImpl` 增加 `ConcurrentHashMap<Long, Object>` 按用户串行化提交订单，将购物车读取与订单写入置于同一用户级临界区。
- 适用边界：**当前单实例部署**有效；多实例扩容时应替换为 Redis 分布式锁或数据库幂等约束。

### 3.4 同一订单并发支付

**修复前（DEF-06）**：两个并发支付均返回成功，产生 2 条 type=1 支付成功通知，存在重复支付/重复通知风险。

**修复后回归**：

| 并发请求 | 响应 | 结果 |
|---|---|---|
| 请求 1 | `code=1`，支付成功 | ✅ 唯一成功 |
| 请求 2 | `code=0`，「订单状态错误」 | ✅ 业务拒绝 |
| 订单最终状态 | `status=2, pay_status=1` | ✅ 只流转一次 |
| type=1 通知 | 1 条 | ✅ 无重复通知 |

- 修复方案：`OrderMapper.updatePayStatusIfPending` 使用 `WHERE id=? AND status=1 AND pay_status=0` 条件更新；`paymentInTransaction` 先校验状态，再以受影响行数判定抢占结果。
- 原始数据：`results/sc15_concurrency_after_fix.txt`。

## 5. 遗留风险

1. `userSubmitLocks` 是单实例 JVM 锁，多实例部署下不能防止重复订单；扩容前需引入 Redis 分布式锁/数据库幂等键。
2. `orders.number` 当前无唯一索引；本轮发现重复订单号风险已由用户级锁缓解，但跨实例或时钟回拨时仍有重复可能，建议评估 `(number)` 或 `(user_id, number)` 唯一约束。
3. Seata TC 不可用时下单约 19s 后才失败，前端体验较差；建议增加 Seata RPC 超时/快速失败策略或显式降级开关。
4. 本轮数据规模仍为摸底级，全量数据下需重跑 SC-13/14/15。
