# 苍穹外卖性能隐患解决方案

> 配套文档：`docs/性能测试方案.md`。
> 本文所有 SQL/配置均建议先在测试库执行并做 `EXPLAIN` 与回归压测，再上生产。

---

## 1. 问题总览与优先级

| # | 隐患 | 影响 | 优先级 | 解决方向 |
|---|---|---|---|---|
| 1 | 下单依赖百度地图 3 次外部 HTTP，GET 无超时 | 下单 RT 不可控，线程/连接被拖死 | P0 | 可配置化 + 超时 + 连接池 + 结果缓存 + 压测 Mock |
| 2 | 订单号用 `System.currentTimeMillis()` 生成 | 高并发下重复，支付/查询可能命中错误订单 | P0 | 唯一订单号生成器 + `number` 唯一索引 |
| 3 | `orders/order_detail/shopping_cart/address_book/dish` 等缺索引 | 大数据量下全表扫描 | P0 | 按实际 SQL 补索引 |
| 4 | 订单分页逐单查 `order_detail`（N+1） | 一页 20 条 = 21 次 SQL | P1 | 批量 `IN` 查询后内存分组 |
| 5 | 报表按天循环 SQL/Feign，导出循环 31 次 | 报表 RT 线性放大，拖垮 order-service | P1 | 按日 `GROUP BY` 一次查回 |
| 6 | 连接池/Redis 池偏小，JVM 未显式配置 | 并发一高就排队或 OOM | P1 | 调大 Druid/Lettuce/Tomcat，补 JVM 参数 |
| 7 | 生产日志过多：Mapper debug、请求级 `log.info` | 日志 IO 成为瓶颈 | P1 | 调级别、热路径改 debug |
| 8 | 网关全局限流规则已按 API 分组补齐 | 原 `sky-gateway-flow-rules.json` 缺失且旧规则失效 | 已完成 | 新增 `sky-gateway-api-group.json` + 重写 `sky-gateway-flow-rules.json`，待导入 Nacos 验证 |
| 9 | 菜品缓存无 TTL、`KEYS` 删除、启停售不清缓存 | Redis 阻塞、数据陈旧 | P2 | TTL + SCAN 删除 + 变更淘汰 |
| 10 | AI 依赖外部 LLM | RT 长、成本高、线程占用 | P2 | 超时/降级/缓存/异步化/压测 Mock |
| 11 | Seata 事务边界偏大、MQ 消息在事务内发送 | 锁持有时间长，极端下消息与事务状态不一致 | P2 | 收缩事务边界，MQ 改 afterCommit |
| 12 | 单实例部署、广播消费者 instanceName 固定 | 无法水平扩容 | P2 | 多副本 + 动态 instanceName + 无状态改造 |

## 2. P0：外部地图依赖治理

### 2.1 现状

`OrderServiceImpl.submitOrder()` → `checkOutOfRange()`，每次下单调用：

1. 店铺地址 geocoding
2. 用户地址 geocoding
3. 驾车路线规划

三个请求都在 `https://api.map.baidu.com`，且 `HttpClientUtil.doGet()` 未设置超时，还每次 `new CloseableHttpClient`。

### 2.2 解决步骤

**第一步：增加超时和连接复用**

`sky-common/src/main/java/com/sky/utils/HttpClientUtil.java`：

```java
private static final RequestConfig DEFAULT_CONFIG = RequestConfig.custom()
        .setConnectTimeout(2000)
        .setConnectionRequestTimeout(2000)
        .setSocketTimeout(3000)
        .build();

private static final CloseableHttpClient HTTP_CLIENT = HttpClients.custom()
        .setDefaultRequestConfig(DEFAULT_CONFIG)
        .setConnectionManager(new PoolingHttpClientConnectionManager())
        .setMaxConnTotal(200)
        .setMaxConnPerRoute(100)
        .disableAutomaticRetries()
        .build();
```

`doGet` 内使用共享 `HTTP_CLIENT`，并给 `HttpGet` 设置 `DEFAULT_CONFIG`。

**第二步：地址和坐标可配置化**

建议新增 `BaiduMapProperties`：

```yaml
sky:
  baidu:
    ak: ${SKY_BAIDU_AK:}
    enabled: true            # 总开关
    mock-enabled: false      # 压测环境置 true，直接返回 800m
    mock-distance: 800
    geocoding-url: https://api.map.baidu.com/geocoding/v3
    direction-url: https://api.map.baidu.com/directionlite/v1/driving
```

`checkOutOfRange()` 优先判断 `mock-enabled`；测试环境不访问百度。

**第三步：缓存地理编码结果**

- 店铺坐标：启动后查一次，永久缓存。
- 用户地址坐标：按 `地址文本 SHA-256` 作为 key 缓存 24 小时。
- 路线距离：按 `(店铺坐标, 用户坐标)` 缓存 30 分钟。

可用 Redis 或 Caffeine，避免每次下单 3 次外部调用变成 0~1 次。

**第四步：地址簿保存坐标（推荐长期方案）**

给 `address_book` 增加 `longitude/latitude`，地址新增/修改时做一次 geocoding；下单时直接用坐标计算直线距离，只有临界值再调用路线规划。这样正常下单可做到 **0 次地图调用**。

## 3. P0：订单号唯一性

### 3.1 现状

```java
orders.setNumber(String.valueOf(System.currentTimeMillis()));
```

同一毫秒两单会重复。支付接口按 `number` 查订单，可能支付到错误订单。

### 3.2 解决

```java
// 示例：时间 + 序列/随机数，或引入雪花 ID/UUID
orders.setNumber(DateTimeFormatter.ofPattern("yyyyMMddHHmmssSSS")
        .format(LocalDateTime.now())
        + String.format("%04d", ThreadLocalRandom.current().nextInt(10000)));
```

然后为订单号加唯一索引：

```sql
-- 先检查历史数据
SELECT number, COUNT(*) FROM orders GROUP BY number HAVING COUNT(*) > 1;

ALTER TABLE orders ADD UNIQUE INDEX uk_orders_number (`number`);
```

## 5. P1：解决订单分页 N+1

### 5.1 现状

`OrderServiceImpl.pageQuery()` 和 `conditionSearch()` 对每页每笔订单执行一次 `orderDetailMapper.getByOrderId()`。`pageSize=20` 时产生 `1+20` 次 SQL。

### 5.2 批量查询方案

`OrderDetailMapper.java` 增加：

```java
List<OrderDetail> listByOrderIds(@Param("orderIds") List<Long> orderIds);
```

新增 XML：

```xml
<select id="listByOrderIds" resultType="com.sky.entity.OrderDetail">
    select * from order_detail
    where order_id in
    <foreach collection="orderIds" item="oid" open="(" separator="," close=")">
        #{oid}
    </foreach>
</select>
```

Service 内：

```java
List<Orders> records = page.getResult();
if (records.isEmpty()) {
    return new PageResult(page.getTotal(), List.of());
}

List<Long> orderIds = records.stream().map(Orders::getId).toList();
Map<Long, List<OrderDetail>> detailMap = orderDetailMapper.listByOrderIds(orderIds)
        .stream()
        .collect(Collectors.groupingBy(OrderDetail::getOrderId));

List<OrderVO> list = new ArrayList<>();
for (Orders orders : records) {
    OrderVO vo = new OrderVO();
    BeanUtils.copyProperties(orders, vo);
    vo.setOrderDetailList(detailMap.getOrDefault(orders.getId(), List.of()));
    list.add(vo);
}
```

效果：一页 20 条从 21 次 SQL 降为 2 次。

## 6. P1：报表/工作台聚合改造

### 6.1 现状

`ReportServiceImpl` 按天循环：

- 营业额统计：N 天 = N 次 `sum(amount)`
- 订单统计：N 天 = 2N 次 `count`
- 用户统计：N 天 = 2N 次 Feign/SQL
- 导出：循环 31 天计算营业数据

### 6.2 改为一次分组查询

`OrderMapper.xml` 增加日聚合：

```xml
<select id="getDailyOrderStats" resultType="java.util.Map">
    select
        date(order_time) as stat_date,
        count(*)                        as total_count,
        sum(case when status = 5 then 1 else 0 end)          as valid_count,
        sum(case when status = 5 then amount else 0 end)      as turnover
    from orders
    where order_time &gt;= #{begin}
      and order_time &lt;= #{end}
    group by date(order_time)
</select>
```

`UserMapper.xml` 增加：

```xml
<select id="getDailyNewUserStats" resultType="java.util.Map">
    select date(create_time) as stat_date, count(*) as new_count
    from user
    where create_time &gt;= #{begin}
      and create_time &lt;= #{end}
    group by date(create_time)
</select>
```

Service 将结果放入 `Map<LocalDate, ...>`，再按日期区间补齐 0 值，代替循环查询。

工作台 `getOrderOverView()` 的 5 次 count 可合并为一条：

```sql
select
    count(*)                                                          as all_orders,
    sum(case when status = 2 then 1 else 0 end)                      as waiting_orders,
    sum(case when status = 3 then 1 else 0 end)                      as delivered_orders,
    sum(case when status = 5 then 1 else 0 end)                      as completed_orders,
    sum(case when status = 6 then 1 else 0 end)                      as cancelled_orders
from orders
where order_time >= #{begin}
```

## 7. P1：连接池、线程池、JVM 参数

### 7.1 Druid

在 Nacos `sky-*-docker.yaml` 的 `spring.datasource.druid` 中：

```yaml
spring:
  datasource:
    druid:
      initial-size: 10
      min-idle: 10
      max-active: 50        # 按压测结果调整，订单服务可先 50
      max-wait: 3000
      test-while-idle: true
      time-between-eviction-runs-millis: 60000
      remove-abandoned: true
      remove-abandoned-timeout: 180
```

同步检查 MySQL：

```sql
SHOW VARIABLES LIKE 'max_connections';
```

6 个服务 × 每实例 50 连接，MySQL `max_connections` 建议 ≥ 500。

### 7.2 Redis Lettuce

`sky-menu-service` / `sky-order-service` / `sky-agent-service` 配置：

```yaml
spring:
  data:
    redis:
      timeout: 2s
      lettuce:
        pool:
          max-active: 32
          max-idle: 16
          min-idle: 4
          max-wait: 2s
```

### 7.3 Tomcat

```yaml
server:
  tomcat:
    threads:
      max: 200
      min-spare: 20
    accept-count: 200
    max-connections: 8192
```

原则：Tomcat 线程数 ≥ 并发请求 × 平均 RT 占比，Druid 连接数 ≤ Tomcat 线程数，且所有服务连接总数不超过 MySQL 上限。

### 7.4 JVM

各 Dockerfile 补充默认 JVM 参数，例如：

```dockerfile
ENV JAVA_OPTS="-Xms512m -Xmx1024m -XX:MaxMetaspaceSize=256m \
-XX:+UseG1GC -XX:MaxGCPauseMillis=100 -Dfile.encoding=UTF-8"
```

`sky-order-service` 在保留 Seata `--add-opens` 的同时追加堆参数；网关和订单服务若压测发现堆不够，可提到 `-Xmx1536m`。

## 8. P1：日志治理

`application.yml` / Nacos 配置统一调整：

```yaml
logging:
  level:
    com.sky.mapper: WARN          # 关闭 SQL debug
    com.sky.gateway.filter: WARN  # 关闭每请求 info
    com.alibaba.cloud.sentinel.endpoint: WARN
```

代码层：

- `JwtAuthGlobalFilter.forwardWithUserContext()` 的 `log.info` 改为 `log.debug`。
- `RocketMQProducerService`、`RocketMQConsumerService` 中每条消息的 `log.info` 改为 `log.debug` 或采样。
- Controller 入口 `log.info("提交订单信息:{}")` 可保留但建议 debug，避免高 QPS 时日志刷盘成为瓶颈。

生产建议使用 logback `AsyncAppender` 异步写文件，控制台降级为 `WARN`。

## 9. P1：网关全局限流规则（已补齐）

当前已新增两个 Data ID：

### 9.1 `sky-gateway-api-group.json`

```json
[
  {
    "apiName": "sky-gateway-all",
    "predicateItems": [
      {"pattern": "/admin/**", "matchStrategy": 1},
      {"pattern": "/user/**", "matchStrategy": 1},
      {"pattern": "/notify/**", "matchStrategy": 1}
    ]
  }
]
```

`matchStrategy=1` 表示 Ant 前缀匹配；多条 predicate 为 OR 关系。当前业务 HTTP 路由全部落在 `/admin`、`/user`、`/notify` 三个前缀下，`/ws/**` 和 `/actuator/**` 不纳入该分组。

### 9.2 `sky-gateway-flow-rules.json`

```json
[
  {
    "resource": "sky-gateway-all",
    "resourceMode": 1,
    "grade": 1,
    "count": 100,
    "intervalSec": 1,
    "controlBehavior": 0,
    "burst": 0
  }
]
```

`resourceMode=1` 表示按 API 分组名称匹配；`grade=1` 表示 QPS 模式；`count=100` 为整个分组每秒合计 100 次。

### 9.3 Gateway 数据源

`application.yml` / `application-docker.yml` 中同时配置：

```yaml
sentinel:
  datasource:
    flow:
      nacos:
        dataId: sky-gateway-flow-rules.json
        rule-type: gw-flow
    api-group:
      nacos:
        dataId: sky-gateway-api-group.json
        rule-type: gw-api-group
```

两个 Data ID 都必须导入 Nacos `DEFAULT_GROUP`；启动后以 Sentinel Dashboard 中“网关流控规则 + API 分组”同时存在为准。

## 10. P2：Redis 缓存治理

### 10.1 设置 TTL

`DishController`：

```java
redisTemplate.opsForValue().set(key, list, Duration.ofMinutes(30));
```

`SetmealController` 目前使用 `@Cacheable`，但未配置 CacheManager。新增：

```java
@Bean
public RedisCacheManager cacheManager(RedisConnectionFactory factory) {
    RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(30))
            .disableCachingNullValues();
    return RedisCacheManager.builder(factory).cacheDefaults(config).build();
}
```

### 10.2 淘汰 `KEYS`，改用 SCAN

`AdminDishController.deletCache()` 当前用 `redisTemplate.keys("dish_*")`。key 多时会阻塞 Redis。改为 SCAN：

```java
private void deleteCache(String pattern) {
    ScanOptions options = ScanOptions.scanOptions().match(pattern).count(200).build();
    redisTemplate.execute((RedisCallback<Object>) connection -> {
        try (var cursor = connection.keyCommands().scan(options)) {
            while (cursor.hasNext()) {
                redisTemplate.delete(cursor.next());
            }
        }
        return null;
    });
}
```

### 10.3 补缓存淘汰

`DishController.setDishStatus()` 中 `//deletCache("dish_*");` 被注释，启停售不会刷新缓存。应恢复调用，并同时清理相关套餐缓存（停售菜品可能导致套餐不可售）。

### 10.4 防冷缓存击穿

`/user/dish/list` 冷启动时，同一分类可能被大量请求同时回源 MySQL。可：

- 对 `setmealCache` 使用 `@Cacheable(sync = true)`；
- 对 `dish_` 手动缓存使用 Redis `SET NX EX` 短锁，拿到锁的请求回源，其余短暂等待后重读。

## 11. P2：AI 助手链路

1. **压测与联调用 Mock LLM**：本地实现 OpenAI 兼容接口，可配置 1~3s 延迟和 tool_call 响应。
2. **配置超时与降级**：给 Spring AI 底层 HTTP 客户端配置 connect/read timeout，避免 LLM 无响应长期占用 Tomcat 线程。
3. **同步接口异步化（可选）**：`chat()` 可改为 `Callable<Result<String>>` / `DeferredResult`，释放 Servlet 线程等待 LLM；SSE 已是响应式返回。
4. **常见问题缓存（可选）**：对“推荐菜品”等高频且结果稳定的 query 做短 TTL 缓存，但 key 需包含 userId 或明确只缓存无状态回答。
5. **保持 Sentinel 5 QPS**：真实模型调用保留资源限流；监控 Tomcat 活跃线程与 LLM P95。

## 12. P2：Seata 与 RocketMQ

### 12.1 缩短事务边界（已实施）

`submitOrder()` 已拆分为：

1. `OrderServiceImpl.submitOrder()`：事务外完成地址查询、地图校验、购物车读取，并在 `OrderTransactionService` 全局事务成功返回后发送 MQ。
2. `OrderTransactionService.submitOrderInTransaction()`：只包含“本地订单写入 + Feign 清空购物车”的 `@GlobalTransactional` 核心方法。
3. `payment()` 同理拆为 `paymentInTransaction()`，MQ 在全局事务返回后发送。

这样全局锁持有时间更短，也避免事务回滚但消息已发出。

### 12.2 消息消费优化

- 消费日志降级为 debug。
- 幂等写入可改为“直接 insert + 捕获 `DuplicateKeyException`”，少一次 `select`；保留唯一索引 `uk_msg_id`。
- 配置消费线程数，例如：

```yaml
rocketmq:
  consumer:
    pull-batch-size: 32
```

并在 RocketMQ Dashboard 观察积压。

### 12.3 广播消费者实例名

`admin-ws-broadcast-instance` 目前固定。多实例部署时应改为动态值：

```java
instanceName = "admin-ws-broadcast-" + "${random.value}"
```

或使用 hostname/PID，避免多个 admin 实例共享同一 MQClient 实例导致广播异常。

## 13. P2：水平扩容与高可用

- 六个业务服务基本无状态，可在 Nacos 健康检查通过后部署 2~3 副本，Gateway `lb://` 自动负载均衡。
- Sentinel 服务端规则是单机维度：扩到 3 个 order-service 实例后，每实例 5 QPS，总容量近似 15 QPS；网关同理。
- 中间件先单机验证容量，再逐步替换为 MySQL 主从/高可用、Redis 哨兵/集群、RocketMQ 多副本、Seata 集群。
- 扩容后需重跑 `docs/性能测试方案.md` 中的混合容量与稳定性场景，确认 Nacos 服务实例数、Feign 负载均衡、WebSocket 广播都正常。

## 14. 实施顺序与验证

### 14.1 建议顺序

1. 压测环境 Mock 百度地图 + Mock LLM（不影响主流程）
2. 关闭 debug/info 日志
3. 补索引（测试库先执行）
4. 唯一订单号改造 + 唯一索引
5. 订单分页 N+1 改造
6. 报表聚合改造
7. 连接池/JVM 调参
8. 网关限流规则补齐
9. Redis TTL/SCAN/淘汰修复
10. Seata/MQ 边界优化
11. 水平扩容验证

### 14.2 每项验证

- SQL：执行计划从 `ALL` 变为 `ref/range`，慢查询消失。
- 接口：压测前后对比 P95/P99、TPS、错误率。
- 数据一致性：下单、支付、取消、再来一单链路对账。
- 中间件：MySQL 连接数、Redis 慢日志/内存、RocketMQ 积压、Seata 锁等待均正常。
- 回滚方案：所有变更通过 Nacos 配置、SQL 脚本和镜像 tag 管理，保留上一版本以便回退。
