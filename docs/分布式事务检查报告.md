## 2. 补齐前代码证据（历史记录）

> 本节保留的是补齐前的检查证据，用于对照。当前代码已按第 6 节补齐。

### 2.1 只有 order-service 接入了 Seata（补齐前）

- 引入 Seata starter 的只有：

```text
sky-order-service/pom.xml
└── spring-cloud-starter-alibaba-seata
```

`sky-cart-service`、`sky-user-service`、`sky-menu-service`、`sky-admin-service` 均无 Seata 依赖。

- `@GlobalTransactional` 只有两处：

```java
// OrderServiceImpl.submitOrder()
@GlobalTransactional(name = "submitOrder", timeoutMills = 60000)
@Transactional
public OrderSubmitVO submitOrder(OrdersSubmitDTO ordersSubmitDTO)

// OrderServiceImpl.payment()
@GlobalTransactional(name = "payment", timeoutMills = 60000)
@Transactional
public OrderPaymentVO payment(OrdersPaymentDTO ordersPaymentDTO)
```

### 2.2 Feign XID 只在发起方传播

Spring Cloud Alibaba Seata starter 提供：

- `SeataFeignRequestInterceptor`：order-service 发起 Feign 时写入 `TX_XID` Header。
- `SeataHandlerInterceptor`：服务端接收 HTTP 时把 `TX_XID` 绑定到 `RootContext`。

但这两个类都由 **Seata starter 自动装配**。cart-service 没有该 starter，因此：

1. 即使 order-service 发来了 `TX_XID`，cart-service 不会绑定到 `RootContext`；
2. cart-service 没有 RM 客户端；
3. cart-service 的 DataSource 没有被 Seata 代理；
4. cart-service 的删除操作不会向 TC 注册分支事务。

### 2.3 清空购物车没有本地事务注解

```java
// ShoppingCartServiceImpl
public void clean() {
    Long userId = BaseContext.getCurrentId();
    shoppingCartMapper.cleanShoppingCart(userId);
}
```

`clean()` 没有 `@Transactional`。即使将来 cart-service 接入 Seata，也需要给该写操作补本地事务边界。

### 2.4 undo_log 覆盖范围

```text
.sql/split/05-sky-order-db.sql  → sky_order_db.undo_log  ✅
.sql/split/01-sky-admin-db.sql  → 无 undo_log
.sql/split/02-sky-user-db.sql   → 无 undo_log
.sql/split/03-sky-menu-db.sql   → 无 undo_log
.sql/split/04-sky-cart-db.sql   → 无 undo_log
```

`.sql/undo_log.sql` 仍指向旧的单体库 `sky_take_out`，在拆分后的部署中没有被使用。

### 2.5 submitOrder 调用链

```text
@GlobalTransactional 开始
  ├─ Feign: user-service 读地址（无写分支）
  ├─ 百度地图 3 次外部 HTTP
  ├─ Feign: cart-service 读购物车（无写分支）
  ├─ orders INSERT          ← 注册 sky_order_db 分支
  ├─ order_detail INSERT    ← 同一分支
  ├─ Feign: cart clean      ← 写操作，但 cart 未接入 Seata，不注册分支
  └─ RocketMQ asyncSend     ← 事务提交前已发送
@GlobalTransactional 结束
```

## 3. 当前具备的能力

在 Seata Server 正常、`sky_order_db` 与 `sky_cart_db` 的 `undo_log` 均已创建、cart-service 已接入 Seata 的前提下：

1. `OrderTransactionService.submitOrderInTransaction()` 中 `orders`、`order_detail` 写入与购物车清空具备跨服务原子性：
   - 任一分支失败，TC 驱动各分支 undo_log 回滚；
   - `after-cart-clean` 故障注入可用于验证购物车恢复。
2. `OrderTransactionService.paymentInTransaction()` 的 `orders` 状态更新具备原子性。
3. order-service 作为 TM/RM，cart-service 作为 RM，可分别向 Seata TC 注册全局事务和分支事务。
4. Seata 客户端配置可用：

```yaml
seata:
  enabled: true
  tx-service-group: sky-order-service-group
  service:
    vgroup-mapping:
      sky-order-service-group: default
    grouplist:
      default: seata:8091
```

5. Seata Server 配置可用：DB 模式 + Nacos 注册 + 认证凭据 + JDBC 驱动挂载。

## 4. 补齐前存在的问题（本次已处理）

### 4.1 订单与购物车不具备分布式原子性

业务语义应是：

```text
下单成功 = 订单落库 + 购物车清空，二者同时成功或同时失败
```

当前如果发生以下顺序：

```text
orders/order_detail 提交成功
→ cart clean 成功
→ 之后出现异常，全局事务回滚
```

实际结果：

- `orders/order_detail` 被回滚；
- `shopping_cart` **已经被清空且无法恢复**。

这是最需要优先确认和修复的事务缺口。

### 4.2 MQ 消息可能早于事务结果

`rocketMQProducerService.sendNewOrderNotification()` 在全局事务提交前调用。若事务最终回滚，管理端仍可能收到“新订单”通知；若服务在提交前崩溃，也可能出现“无订单但有通知”。

### 4.3 外部 HTTP 在全局事务内

百度地图 3 次调用位于 `submitOrder()` 的 `@GlobalTransactional` 方法内。虽然此时尚未注册本地分支，但全局事务计时已经开始。外部调用无超时会进一步放大事务超时风险。

### 4.4 缺少回滚测试注入点

没有默认关闭的故障开关，也没有统一测试钩子，导致：

- 无法精确模拟“orders 写入后失败”；
- 无法精确模拟“购物车清空后失败”；
- 无法验证购物车是否能恢复。

## 5. 运行时验证方法

### 5.1 环境启动后验证基础能力

```bash
# 1. MySQL 已初始化 .sql/split 脚本（含 cart undo_log）
# 2. 启动 Seata 与两个业务服务
docker compose up -d seata sky-cart-service sky-order-service
```

发起一笔正常下单后查询 Seata 库：

```sql
SELECT xid, application_id, transaction_service_group, status
FROM seata.global_table
ORDER BY gmt_create DESC LIMIT 10;

SELECT xid, branch_id, resource_id, branch_type, status
FROM seata.branch_table
ORDER BY gmt_create DESC LIMIT 20;
```

**补齐后预期**：一笔 `submitOrder` 应有 **2 个分支**：order-service 的 `sky_order_db` 分支 + cart-service 的 `sky_cart_db` 分支。若仍只有 1 个分支，需检查 cart-service 是否加载了 Seata 配置、`undo_log` 是否存在、`clean()` 是否经过 Spring 代理。

### 5.2 购物车是否参与事务的判定

下单前后对比：

```sql
SELECT COUNT(*) FROM shopping_cart WHERE user_id = ?;
```

如果人工制造订单回滚后购物车未恢复，即可复现 4.1 的问题。

### 5.3 制造回滚故障（推荐使用 SeataFaultInjector）

给 `sky-order-service` 设置 JVM 参数或环境变量：

```bash
JAVA_TOOL_OPTIONS="-Dtest.seata.fault-point=after-cart-clean"
# 或 Nacos 配置中增加 test.seata.fault-point
```

关键用例：

| 故障点 | 预期 |
|---|---|
| `after-order-insert` | 订单、明细都不存在；购物车不变 |
| `after-order-detail` | 订单回滚，明细不存在；购物车不变 |
| `before-cart-clean` | 订单/明细回滚；购物车不变 |
| `after-cart-clean` | 订单/明细回滚；**购物车恢复为下单前快照** |
| `after-payment-update` | 订单支付状态保持未支付 |

通过后应检查：

- `seata.lock_table` 无测试残留；
- `sky_order_db.undo_log`、`sky_cart_db.undo_log` 无未清理记录；
- 同一用户可再次成功下单。

## 6. 已实施的补齐内容

### 6.1 cart-service 接入 Seata

`sky-cart-service/pom.xml` 增加：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-seata</artifactId>
</dependency>
```

Nacos `sky-cart-service-dev.yaml` / `sky-cart-service-docker.yaml` 增加：

```yaml
seata:
  enabled: true
  tx-service-group: sky-order-service-group
  service:
    vgroup-mapping:
      sky-order-service-group: default
    grouplist:
      default: ${SEATA_SERVER_ADDR:127.0.0.1:8091}
```

Docker 配置中 `${SEATA_SERVER_ADDR}` 设为 `seata:8091`，或直接写 `seata:8091`。

### 6.2 sky_cart_db 增加 undo_log

复制 `.sql/split/05-sky-order-db.sql` 中的 `undo_log` DDL 到 `sky_cart_db`。

### 6.3 购物车清空方法加本地事务

```java
@Transactional(rollbackFor = Exception.class)
public void clean() {
    Long userId = BaseContext.getCurrentId();
    shoppingCartMapper.cleanShoppingCart(userId);
}
```

### 6.4 MQ 改为全局事务成功后发送

`OrderServiceImpl` 不再在事务方法内发送 MQ，而是在 `OrderTransactionService` 的 `@GlobalTransactional` 方法成功返回后再发送。这样全局事务提交/回滚结果已确定，避免使用本地事务 `afterCommit`（Seata AT 分支在全局提交前就会触发本地 afterCommit，无法代表全局结果）。

### 6.5 外部地图调用移出事务边界

已实施：地址查询、百度地图校验、购物车查询都留在 `OrderServiceImpl.submitOrder()`，只有订单写入、明细写入和 Feign 清空购物车进入 `OrderTransactionService.submitOrderInTransaction()` 全局事务。

### 6.6 增加故障注入开关

已实施：新增 `com.sky.fault.SeataFaultInjector`，通过 `test.seata.fault-point` 注入异常，默认 `none`。支持注入点：

```text
after-order-insert | after-order-detail | before-cart-clean | after-cart-clean | after-payment-update
```

## 7. 补齐后结论

- 代码层面已具备“订单 + 购物车”分布式事务所需组件：order-service 作为 TM/发起方，cart-service 作为 AT 分支参与者。
- 全局事务边界已收窄到 `OrderTransactionService` 的两个写方法；地图调用和购物车读取不再占用事务。
- MQ 通知在全局事务方法成功返回后发送，回滚场景不会发出新订单/支付成功通知。
- `SeataFaultInjector` 已提供 5 个默认关闭的故障注入点。
- **仍需运行时验证**：数据库导入新 `undo_log`、Nacos 导入 cart-service 新配置、重启服务后，确认一笔下单在 `seata.branch_table` 中产生 2 个分支，并通过 `after-cart-clean` 故障注入验证购物车可回滚恢复。
