# 苍穹外卖 QPS 瓶颈突破方案（基于实测）

> 配套：`docs/性能测试报告-缓存与Sentinel对比.md`（三阶段基线）
> 实测环境：WSL2 + Docker，16 核；被测链路 gateway→menu-service→MySQL

## 1. 瓶颈定位结论（实测依据）

| 疑点 | 实测结论 |
|------|---------|
| 数据库连接池 | ❌ 非瓶颈（Druid 20 只用 7~8，Threads_running 0~2） |
| MySQL 查询 | ❌ 非瓶颈（单请求仅 4ms） |
| CPU | ❌ 非瓶颈（全程 ~21%） |
| WSL2/容器网络 | ❌ 非瓶颈（容器内压测 = 宿主机压测，~507 vs ~510 QPS） |
| **Spring MVC 同步阻塞 + 路径变量全量遍历** | ✅ **主要瓶颈** |
| **Tomcat 默认线程池(200) 高并发竞争** | ✅ **次要瓶颈**（并发越高吞吐越低） |

**核心根因**：
- Spring MVC 一个请求占一个 Tomcat 线程（同步阻塞模型）。
- `menu-service` 存在**路径变量接口**（`/user/setmeal/dish/{id}`、`/admin/*/{id}`、`*/status/{status}` 等），这类映射**无法命中 direct-path 缓存，每次请求都要全量遍历所有 handler mapping 做模式匹配**（jstack 证实卡在 `AbstractHandlerMethodMapping.addMatchingMappings`）。
- 高并发下多线程同时遍历同一个 HashMap + Tomcat 线程竞争，导致"并发越高吞吐越低"。

## 2. 已实测验证有效的方案（按性价比排序）

### ① 调大 Tomcat 线程池（最直接、立竿见影）✅ 已完成（menu-service）
`server.tomcat.threads.max` 从默认 200 提到 400，并适当放宽连接参数：
```yaml
server:
  tomcat:
    threads:
      max: 400        # 200 → 400
      min-spare: 50
    accept-count: 500
    max-connections: 10000
```
**实测效果**（sat_thread 可靠客户端，category 直接压 8084）：
| 并发 | 默认线程(200) | 调大线程(400) |
|:---:|:---:|:---:|
| 40 | ~510 QPS | **803 QPS** |
| 80 | ~290 QPS | **677 QPS** |
| 160 | ~166 QPS | **609 QPS** |

> 注意：调大线程会占用更多内存（每线程约 1MB 栈 + 上下文），需结合内存评估；若仍不足再往上调。

### ② 消除路径变量导致的全量 mapping 遍历（针对根因）✅ 已完成（全部微服务 + Feign）

已覆盖 **menu / admin / user / order** 四个微服务所有路径变量接口，并同步更新 **Feign 客户端**指向精确路径：
- menu：`/user/setmeal/dish`、`/admin/*/detail`、`/admin/*/status`
- admin：`/admin/employee/detail`、`/admin/employee/status`
- user：`/user/user/detail`、`/user/addressBook/detail`
- order：`/user/order/orderDetail|cancel|repetition|reminder`、`/admin/order/details|delivery|complete`、`/admin/shop/status`
- Feign：`MenuFeignClient`、`UserFeignClient` 已改走精确路径（调用方方法签名不变）
- 所有旧路径变量接口均保留（向后兼容）
把高频路径变量接口改为**精确路径 + 查询参数**，命中 direct-path 缓存：
```java
// 之前（路径变量，触发全量遍历）
@GetMapping("/dish/{id}")
public Result<List<DishItemVO>> dishList(@PathVariable("id") Long id) { ... }

// 之后（精确路径，命中 direct-path 缓存）
@GetMapping("/dish")
public Result<List<DishItemVO>> dishList(@RequestParam("id") Long id) { ... }
```
**实测效果**（40 并发，3 次中位数）：
| 接口 | 中位 QPS |
|------|:---:|
| 精确路径 `/user/setmeal/dish?id=32` | **648** |
| 路径变量 `/user/setmeal/dish/32` | **473** |

> 已给 `sky-menu-service` 新增 `/user/setmeal/dish`（精确路径）接口，旧接口保留向后兼容。前端可平滑迁移。
> 同时检查是否还有 `*.do` 后缀等导致匹配失败的写法（本项目无此问题，但需注意）。

### ③ 综合 ①② 的整体收益
80 并发经网关压 category：**~290 → ~742 QPS（约 2.5 倍）**。

## 3. 进一步突破（需要更大改动，按收益/成本）

### ③ JDK 21 + 虚拟线程（Virtual Threads）
- Spring Boot 3.5 原生支持，收益来自"线程即资源"的解放，官方基准**吞吐 +50%**。
- 需要：基础镜像 `eclipse-temurin:17-jre` → `21-jre`，加配置 `spring.threads.virtual.enabled=true`。
- 注意：本项目要求 JDK 17 起步，升级到 21 需回归验证 Lombok/Seata 等兼容性。

### ④ 异步化（DeferredResult / Callable / WebFlux）
- 适用**存在慢阻塞调用**的场景（外部 HTTP、长 SQL）。本项目核心读接口是纯 DB 查询（~4ms），异步收益有限。
- 若未来引入外部调用（如订单的百度地图/微信支付），可对这类接口做异步化，释放 Tomcat 线程。

### ⑤ 换 WebFlux（架构级）
- gateway 已是 WebFlux/Netty。若业务服务也换 WebFlux，彻底摆脱"一请求一线程"模型。
- 收益最大但改造成本最高（阻塞式 MyBatis/ThreadLocal 需重构），仅在高并发 I/O 密集场景值得。

### ⑥ 缓存与静态化（突破框架瓶颈后才会成为重点）
- 当前瓶颈在框架层，缓存只带来 ~10%（DB 不是瓶颈）。
- 一旦框架瓶颈解决（线程/路径优化），DB 查询占比上升，再扩充缓存（category/setmeal 也加 Redis/Caffeine）收益会更明显。

### ⑦ 多实例水平扩展
- 微服务天然支持多副本。当前单实例 ~550 QPS，加 2~3 个实例（配 gateway 负载均衡）可线性扩展。
- 这是**性价比最高、最稳妥**的突破方式（配合 Sentinel 保护、K8s 弹性）。

## 4. 推荐的落地顺序

1. **先做 ①调线程 + ②路径优化**（已实测，改动小、收益明确）→ 单实例冲到 ~700-800 QPS
2. **再评估 ③虚拟线程（JDK21）**（收益大、改动中等）
3. **架构演进**：多实例水平扩展（立即可做）→ 需要时再考虑 WebFlux
4. 全程配合 **Sentinel 限流/熔断**保护，避免超载（实测当前瓶颈下 Sentinel 空载损耗可忽略）

## 5. 相关改动清单（本次已落地，向后兼容）

- `sky-menu-service` 新增精确路径接口 `/user/setmeal/dish?id=`（保留旧 `/dish/{id}`）
